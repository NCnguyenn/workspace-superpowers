# Deliverable Contract

<!-- Planning instructions: remove from a user-facing contract. -->
Use this template when a task has several outputs, an editable source plus an export, or acceptance checks that must be agreed and checked separately. The executing agent prepares it from the authorized brief and keeps it consistent with any adopted work plan. It is not mandatory for a one-off answer or isolated edit and does not create another approval gate. Declare only outputs actually requested or authorized. A usable contract names each output's path, format, role, source revision/relationship, and observable acceptance check; unknown paths or evidence remain pending rather than invented. Omit unused output categories.

## Declared Outputs

### 1. Primary Source / Editable Artifacts
* **Path:** [Exact authorized output path; pending if not decided]
* **Format:** [e.g., DOCX / Markdown / XLSX / PPTX]
* **Role:** Source of truth for editing and maintenance
* **Source / Revision:** [Input revision and intended working revision; preserve adopted user edits]

### 2. Rendered / Exported Artifacts
* **Path:** [Exact export path when requested]
* **Format:** [e.g., PDF / PNG]
* **Role:** Final deliverable or presentation format
* **Source / Revision Relationship:** [Editable source ID and exact revision used for export; note stale exports]
* **Verification Note:** Verified independently from source artifact [actual check ID/result or pending]

### 3. Supporting Assets & Data
* **Path:** [Authorized assets, citation data, figures, or datasets actually needed]
* **Role:** Referenced citations, charts, raw data, or figures
* **Provenance / Reuse:** [Source locator, rights/limits and relevant asset ID; pending when unknown]

## Verification Criteria

For tables and figures apply [visual assets and Word fidelity](../references/visual-assets-and-word-fidelity.md). Record the target revision and approval state, asset/table identities, and paragraph-relative output locators in this existing contract or reference their authoritative record. For DOCX distinguish actual structural, rendered, and native-host checks; an unavailable check is `unverified`, not a pass. Define acceptance as observable properties before claiming it, then reopen every delivered file after the last change.

* **Integrity Checks:** [Specific format, layout, page break, font/style, embedded media, formula, or link checks required; target revision and pass condition]
* **Evidence Consistency:** [Cross-artifact comparisons, source locators, measured versus illustrative limits]
* **Acceptance / Blocking Gaps:** [Required checks and who can resolve missing source, permission, or capability]
* **Honesty Rules:**
  - Artifact re-inspection is mandatory before claiming completion.
  - Command success alone is never artifact success; record failed and unrun checks as well as passed ones.
  - If rendering or visual capability is unavailable, state the unchecked properties explicitly. Do not substitute an invented verification claim.
